1. Как выполняется полный перевод текста (режим full)
Полный перевод — это режим translation.mode: full. Обрабатывается в TranslationPipeline._full (pipeline.py:120) и состоит из такой последовательности:

Поиск сущностей — find_table_mentions() находит в вопросе вхождения значений из таблицы (подробно в п.3).
Маскирование — mask_question() заменяет каждый найденный фрагмент на неизменяемый плейсхолдер вида <TABLE_REF_0000>, <TABLE_REF_0001> и т.д. Плейсхолдеры вставляются в обратном порядке (справа налево), чтобы не смещались индексы.
Перевод «оболочки» вопроса — translate_shell() отправляет замаскированный текст в LLM одним запросом (task через system-промпт SHELL_TRANSLATION_SYSTEM). Модель переводит только естественно-языковой текст, обязана сохранить все <TABLE_REF_XXXX> символ-в-символ. Ответ проверяется validate_masks(): плейсхолдеры не должны исчезать/дублироваться/добавляться.
Перевод таблицы — translate_table() (без аргумента columns, т.е. все столбцы) отправляет один LLM-запрос со списком уникальных переводимых значений values=[{id,text},...]. Это v0.8-механика «словаря уникальных значений»: Python сам извлекает только уникальные текстовые значения, не отправляет модели ни строки, ни столбцы, ни координаты, ни immutable-значения, ни невыбранные столбцы. Модель возвращает translations=[{id,translation},...], ответ строго валидируется по множеству ID (пропущенные/лишние/дублированные ID, пустые переводы, лишние JSON-поля — отклоняются), затем Python вставляет переводы по сохранённым координатам.
Восстановление — restore_from_table() подставляет переведённые значения таблицы вместо масок в переведённый текст вопроса.
Перевод ответа — build_target_value() строит целевое значение ответа (по координатам в таблице).
Обратный перевод (обязательный) — back_translate_shell() переводит переведённый вопрос обратно на исходный язык, затем restore_original() подставляет исходные фрагменты вопроса; back_translate_table() обратно переводит таблицу тем же словарным механизмом. Проверяется точная реконструкция исходного вопроса и метрики качества обратного перевода.
Диагностика — опциональная косинусная близость вопроса через отдельный embedding-провайдер (_score_question).
 Примечание (актуальный candidate-based full-путь): перевод таблицы идёт через translate_table_candidates() по ярусам-подпоследовательностям. Ярусы обрабатываются от большего к меньшему; каждый кандидат отправляется отдельным item'ом {"id","text","column","glossary"}, где column — полный оригинальный заголовок столбца первой координаты (только контекст, не переводится), а glossary — переводы самых длинных уже переведённых более длинных последовательностей, в которые вложен данный текст. Домен таблицы указывается один раз в системном промпте переводов кандидатов, а не в user-JSON; формат ответа остаётся {"translations":[{"id","translation"}]}. Обратный перевод таблицы (back_translate_table_candidates) использует ту же логику с обратным направлением языков.
Каждый LLM-запрос (плюс retry и ответы из кэша) пишется в runs/<run_id>/reports/llm_io.jsonl с полями question_id, stage, attempt. Стадии: translate_shell, translate_table.values, back_translate_shell, back_translate_table.values.

Повторный запрос выполняется только если ответ невалиден или не проходит детерминированные проверки, в пределах model.retries.

2. Какие настройки относятся к полному переводу
Ключевые секции конфига (AppConfig, config.py):

translation:
mode: full — сам режим.
answer_language_mode (table / question) — на каком языке должен быть ответ.
project:
source_language, target_language — направление перевода (в qwen_full.yaml: en → ru).
seed — детерминированность (влияет на seed каждого LLM-вызова).
model — параметры LLM: provider, base_url, api_key, model_name, temperature, max_output_tokens, timeout_seconds, retries (количество повторных попыток при невалидном ответе).
mentions — настройки поиска сущностей (влияют на маскирование, подробно в п.3).
table.rows_per_chunk — в v0.8 сохранён только ради совместимости конфигов, на фактический перевод таблицы не влияет.
back_translation.enabled — обязательный (валидатор resolve_and_validate запрещает false).
validation:
strict_masks — жёсткая проверка плейсхолдеров.
strict_table_shape — проверка неизменности формы таблицы.
strict_immutable_values — запрет изменения immutable-значений.
question_cosine_enabled — включает/выключает косинусную проверку вопроса (дефолт true).
question_bert_enabled — включает BERT-проверку вопроса (работает только при bert_score.enabled; дефолт true).
back_table_bert_enabled — включает BERT-проверку обратно переведённой таблицы (работает только при bert_score.enabled; дефолт true).
question_cosine_threshold — порог косинусной близости обратного перевода (в qwen_full.yaml — null, т.е. не задан, только диагностика).
back_table_similarity_enabled — включает/выключает семантическую проверку обратного перевода таблицы.
back_table_similarity_mode — гранулярность сравнения: context (заголовок + жадные чанки строк, дефолт), row (заголовок и каждая строка отдельно), cell (каждая ячейка отдельно).
back_table_similarity_threshold — опциональный порог схожести: если задан и min ниже → warning + NEEDS_REVIEW (по умолчанию null — только диагностика).
back_table_similarity_max_chunk_tokens — бюджет токенов для чанков в режиме context (используется только там).
embeddings — enabled, model_name и т.д. для косинусной близости.
cache — SQLite-кэш chat/embedding запросов.
runner — checkpoint_every, continue_on_error, retry_failed_on_resume, rerun_needs_review (управление прогоном датасета).
Immutable-значения определяются в validation/invariants.py: пустые строки, числа (123, 1,234, 12.5%), URL (http(s)://…, www.), и идентификаторы вида AB-12 / Foo_123. Они никогда не отправляются в LLM и не должны меняться.


### BERT-score (вопрос и таблица)

Опциональная параллельная оценка качества обратного перевода через `bert-score`. Мастер-включатель `bert_score.enabled` (в `qwen_full.yaml` — `true`, по умолчанию `false` — torch не импортируется). Каждый сайт дополнительно включается своими флагами в `validation:` (`question_bert_enabled`, `back_table_bert_enabled`).

- **Вопрос**: `score_bertscore_pair` сравнивает переведённый вопрос с обратным переводом; поля отчёта `question_bert_f1/precision/recall`. Порог `bert_score.question_threshold` — если задан и `f1` ниже → warning + `NEEDS_REVIEW`; null = только диагностика.
- **Таблица** (`score_bertscore_table`): те же единицы сравнения, что и у косинусного скоринга (`context`/`row`/`cell`, `back_table_similarity_mode`); нормализованно совпавшие единицы дают полный балл без вызова модели; per-unit агрегация min/mean по F1/precision/recall → поля `back_table_bert_groups_compared`, `back_table_bert_min/mean_f1`, `back_table_bert_min/mean_precision`, `back_table_bert_min/mean_recall`. Порог `bert_score.table_threshold` — по `min_f1` → warning + `NEEDS_REVIEW`.

```yaml
bert_score:
  enabled: true
  model_type: bert-base-multilingual-cased
  lang: multilingual
  device: cpu        # cpu | cuda | cuda:N | mps
  batch_size: 64
  rescale_with_baseline: false
  question_threshold: null
  table_threshold: null
```

Деградация: при ошибке загрузки модели / инференса (нет torch, нет сети для скачивания весов HF) поля остаются `None`, пишется warning, статус не меняется. Модель загружается лениво и кэшируется (один раз на процесс); синхронный инференс выполняется через `asyncio.to_thread`, поэтому при включённом BERT рекомендуется держать `runner.concurrency` умеренным (конкуренция за GPU/потоки). Путь HF-кэша — стандартный; `rescale_with_baseline: true` требует файл baseline-idf. Берт-score тянет torch (~сотни МБ); в CI-окружении без GPU BERT отключаем.

3. Как ищутся в тексте сущности из таблицы
Поиск выполняет find_table_mentions() (mentions/finder.py), строго детерминированно и без LLM (настройки allow_lemma_match, allow_fuzzy_match, allow_semantic_match принудительно false — валидатор deterministic_mvp это требует, MVP поддерживает только точное совпадение после нормализации).

Алгоритм:

Нормализация (normalize.py): к тексту вопроса и каждому значению таблицы применяется MentionNormalizationConfig:
unicode: NFKC (совместимость символов, раскрытие лигатур),
casefold: true (регистронезависимо),
collapse_whitespace: true (схлопывание пробельных последовательностей),
strip_outer_punctuation: true (снятие краевой пунктуации только у кандидатов из таблицы, не у вопроса — чтобы сохранить корректное сопоставление спанов).
Сбор кандидатов (_build_candidates): из таблицы берутся заголовки (include_headers: true) и все ячейки. Числа могут включаться/исключаться через include_numeric_mentions: true (_is_numeric проверяет, парсится ли значение как float после удаления запятых). Пустые после нормализации значения пропускаются.
Поиск вхождений (_collect_hits): каждый нормализованный кандидат ищется в нормализованном вопросе через regex с экранированием (re.escape). Есть защита от случайных подстрок (например, заголовок A внутри слова Was): совпадение не должно граничить с буквенно-цифровым символом. При этом сохраняется обратное сопоставление нормализованного текста к исходным спанам (normalize_with_mapping), чтобы получить координаты в исходной строке.
Выбор максимальных фрагментов (_select_maximal_non_overlapping): применяется правило longest-match-first / maximal-fragment — сортировка по убыванию длины, выбираются непересекающиеся спаны. Это важно: длинное неоднозначное совпадение (например New York City) блокирует вложенные короткие (York), а не молча маскирует только вложенный фрагмент.
Группировка и разрешение неоднозначности:
Совпадения с одинаковым спанов и нормализованным текстом группируются.
Группа однозначна (is_resolvable), если: координата одна, либо все вхождения — ячейки в одном столбце (повторяющиеся одинаковые значения в одном столбце сохраняются как одно логическое упоминание со всеми координатами; позже Python требует, чтобы их переводы совпадали перед вставкой в вопрос).
Иначе фрагмент помечается как ambiguous — LLM-угадывание запрещено, координата не выбирается автоматически.
Неоднозначность обрабатывается через mentions.on_ambiguity (needs_review / failed): при failed вопрос падает с ошибкой, при needs_review результат помечается NEEDS_REVIEW (а сам фрагмент не маскируется — он остаётся в переводимом тексте).
Результат — список TableMention с полями mask, question_text (точный исходный фрагмент, включая регистр/пунктуацию), normalized_text, start/end, source_type (header/cell) и coordinates. Именно этот список используется для маскирования (mask_question) и последующего восстановления (restore_from_table / restore_original). Точная реконструкция исходного вопроса после обратного перевода проверяется детерминированно.
